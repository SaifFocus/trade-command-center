# AGENTS.md
- Backtest engine `src/lib/hl/engine.ts` is pure and deterministic; data is loaded per coin via the `hl_backtest_data` RPC (funding pre-bucketed to 4h). Why: avoids row-limit pagination and keeps the engine testable.
- Single-owner app: `public.app_owner` + `public.is_owner()`; every table has only an owner SELECT policy, clients have no write grants, and every server function uses `requireSupabaseAuth` + `assertOwner` before service-role work. Why: nobody but the owner may read, write or trigger anything.
- All pages live under `src/routes/_authenticated/` (signed-in gate + owner gate); only `/login` is outside. Why: no public surface.
- The cron route requires `x-cron-secret`, verified via service-role-only `verify_cron_secret()` against `public.app_private`; pg_cron reads the same row. Why: token never leaves the server/DB.
- Risk rules are pure functions in `src/lib/hl/risk.ts` with tests in `risk.test.ts`. Why: easy to check and change.
- `submit_review()` can only be executed by service_role/postgres. Why: only the owner's external agent may review, via SQL.
- Live desk (real money): `src/lib/live/*`. Rules are pure in `live-risk.ts` (tests in `live-risk.test.ts`); `live.server.ts` does all I/O; `hl-exchange.server.ts` is the only file that reads `HL_AGENT_PRIVATE_KEY`. Why: one place touches the key, every rule is testable.
- `/api/cron/live-reconcile` runs every 2 minutes: fills, stops, break-even, mirrored time/follow exits, retries of unfinished closes, safety trips. Three failed safety checks in a row, or a 15% loss, call `killLive`. Any writer setting `kill_switch = true` flattens live on the next reconcile. `executeLive` and `reconcileLive` share the `live_lock` lease. Why: one kill path for the button, the watchdog and SQL; no stale views.
- Research connectors (CoinMarketCap, LunarCrush) are used only by the scheduled signal-review agent, never by app code. Coinversa Pulse is a fallback candidate source, used only if the Hyperliquid copy gate fails (`docs/fallback/coinversa-candidates.sql`, not applied). Why: wallet scores come only from Hyperliquid's own data.
- Navigation: every signed-in page renders inside `AppShell` (sidebar + Ctrl/Cmd+K palette) from `_authenticated/route.tsx`; menu groups live only in `src/components/nav/nav-config.ts`, so pages don't add their own nav links. Restore sidebar preference after hydration; mobile navigation closes its drawer after selection. Content Rewards is a separate company (contentrewards.com) that uses Whop only for payouts; its 10% creator fee comes off CPM payouts (`WHOP_FEE_PCT` in `src/lib/cr/logic.ts`). Why: one menu to maintain, and estimates match the terms.
- Strategy research runs offline in `research/strategy-lab/` (Python, data exported from `hl_candles`/`hl_funding`). A setup is adopted only after the engine re-implementation matches the lab on the same data and passes both halves of an uncapped backtest. Why: fast experiments without research code in the app, and backtest numbers that don't depend on which coins happened to get the slots.
- Owner's sizing rule `SIZE_UP` (`src/lib/hl/risk.ts`, also used by `sizeLive`): when the reviewer's confidence (review.confidence, chance of reaching T1 before the stop) is 70 or more and the normal size is too small to split into two halves above the $10 minimum, the trade is sized up just enough to split, never above $40, and the max-risk check is skipped for that step. The night rule is off (owner wants entries 24/7). Why: the owner accepts a larger position only on high-confidence trades so T1/T2 can split on small accounts.

- Subdirectories have their own `AGENTS.md`; read the relevant scoped rules before changing their files or related callers. Rules for market data, engine, and paper desk: `src/lib/hl/AGENTS.md`; live I/O: `src/lib/live/AGENTS.md`; Scout, Invo bridge, and Mimic (including `bridge/` and Invo routes): `src/lib/sm/AGENTS.md`; Content Rewards writes: `src/lib/cr/AGENTS.md`. Why: preserve detailed rules without loading unrelated subsystems every turn.
- Campaigns uses URL-backed filters and sorting, Query loader priming, and a shared campaign-input schema for owner writes. Why: reloads preserve the view and client/server validation stays consistent without changing trading logic.
- Clip Pipeline and Approvals share `ClipReview` and loader-primed, paginated clip reads; owner review uses tested `clip-review` rules and conditional stage/timestamp updates. Why: identical spec review on both surfaces, no truncated queue, and no lost concurrent agent notes or duplicate decisions.
- Agent and account writes share tested `management-input` schemas; pages prime Query data, and agent controls only save external-agent configuration. Why: consistent validation without implying jobs run or social linking is verified by APEX.

- Overview and Earnings prime Query loaders; posts are read in deterministic pages, and shared pure reporting rules separate observed views from unavailable verified counts, net USD estimates from recorded payouts, and denied/unknown/active earning windows. Why: no truncated ledger, invented verification or divergent totals.
