# AGENTS.md

- Hyperliquid market data is fetched only from the public info API in `src/lib/hl/*.server.ts` and written with the service-role client. Why: no keys/wallets, writes only from server code.
- Full sync runs one coin per server-function call (UI loops); the cron route `/api/cron/hl-sync` does incremental sync and self-throttles (skips if synced < 30 min ago). Why: worker request time limits.
- Backtest engine `src/lib/hl/engine.ts` is pure and deterministic; data is loaded per coin via the `hl_backtest_data` RPC (funding pre-bucketed to 4h). Why: avoids row-limit pagination and keeps the engine testable.
- Single-owner app: `public.app_owner` + `public.is_owner()`; every table has only an owner SELECT policy, clients have no write grants, and every server function uses `requireSupabaseAuth` + `assertOwner` before service-role work. Why: nobody but the owner may read, write or trigger anything.
- All pages live under `src/routes/_authenticated/` (signed-in gate + owner gate); only `/login` is outside. Why: no public surface.
- The cron route requires `x-cron-secret`, verified via service-role-only `verify_cron_secret()` against `public.app_private`; pg_cron reads the same row. Why: token never leaves the server/DB.
- A trigger on `auth.users` rejects sign-ups once an owner exists. Why: auth-level sign-up block.
- Paper desk: `src/lib/hl/desk.server.ts` runs cycle (sync, FX, manage, signals) and execute (expire, shadow, risk, fill); cron routes `/api/cron/desk-cycle` and `/api/cron/desk-execute` replace the old hl-sync job. Why: the review window has to sit between signal creation and execution.
- Trade management (`stepPosition`) and signals (`signalsAt`, `regimeAt`) live only in `engine.ts` and are shared by backtest and paper desk. Why: paper results have to match the backtest.
- Risk rules are pure functions in `src/lib/hl/risk.ts` with tests in `risk.test.ts`. Why: easy to check and change.
- `submit_review()` can only be executed by service_role/postgres. Why: only the owner's external agent may review, via SQL.
- agent_logs.level only allows INFO/SIGNAL/WARNING/ERROR; desk logs are mapped to those. Why: there's a check constraint on the existing table.
- Live desk (real money): `src/lib/live/*`. Rules are pure in `live-risk.ts` (tests in `live-risk.test.ts`); `live.server.ts` does all I/O; `hl-exchange.server.ts` is the only file that reads `HL_AGENT_PRIVATE_KEY`. Why: one place touches the key, every rule is testable.
- Live only trades signals the paper desk just filled (`runExecute` → `executeLive`). `desk_config.live_armed` is the switch; `mode` is display ('paper' or 'live'), and paper keeps trading in both. Why: paper stays the comparison.
- `/api/cron/live-reconcile` runs every 2 minutes: fills, stops, break-even, mirrored time/follow exits, retries of unfinished closes, safety trips. Three failed safety checks in a row, or a 15% loss, call `killLive`. Any writer setting `kill_switch = true` flattens live on the next reconcile. `executeLive` and `reconcileLive` share the `live_lock` lease. Why: one kill path for the button, the watchdog and SQL; no stale views.
- Hyperliquid's $10 minimum applies to every order except a reduce-only order that closes the whole position, so T1/T2 split only when both halves clear it. `live.sim.test.ts` runs the whole flow against `testing/fakes.ts`. Keep it passing before touching live code.
- Paper universe = top 20 perps by volume + always-on coins + `desk_config.paper_extra_coins`. Extras come only from `/api/cron/desk-universe` (`universe.server.ts`): it backfills ranks 21–40, backtests them as a group (rules in pure `universe.ts`, tests in `universe.test.ts`) and writes the coins that pass. Risk-blocked approved signals become shadow positions with `shadow_reason = 'risk'`; vetoed ones get `'vetoed'`. Why: more practice trades on paper without touching live, and veto value stays measurable.
- Practice follows: `rebuildWatchlist` adds up to 20 swing traders (score ≥ 3) below the A/B bar (`sm_scores.practice`); their opens become `practice_follow` signals (paper only, never in consensus counts, hard-blocked in `liveEntryBlock`). The grading queue serves watched wallets, then Invo traders (originators first), then the leaderboard. Why: learn from Invo traders daily without touching real money.
- Scouted Invo traders: real-money Invo portfolios the owner asked to follow, matched to their Hyperliquid wallet (open positions and recent fills must line up), are tagged `'invo_scout'` in `sm_wallets.sources` with the Invo username in `display_name`. `scoutedAddresses()` (max `SCOUT_SLOTS` = 30) makes them practice wallets outside the 20 practice slots and always-mirrored Mimic wallets; their opens count from 0.5% of account value (`SCOUT_MIN_FRAC`) and carry `regime = 'invo_scout_open'`. Paper only. The match is done offline from the Invo site; app code never calls Invo or stores Invo credentials. Why: follow what proven Invo traders do, on-chain and credential-free.
- Invo bridge (`bridge/`, installed on the owner's Windows PC in Documents\APEX Invo Bridge): Node + playwright-core drives the installed Edge with its own profile, logged into Invo by the owner. Each round it opens every followed portfolio (in-app navigation, full load as fallback, scrolls for more) and posts every JSON response from `capture_hosts` to `/api/invo/ingest` (gzip, `x-bridge-secret`; APEX stores only the secret's SHA-256 in `app_private` 'invo_bridge_secret_sha256'). Targets, URLs, hosts and timing come from `/api/invo/targets`, so Invo changes are fixed in APEX, not on the PC. Parsing is content-based and pure (`invo-parse.ts`, tests in `invo-parse.test.ts`): positions are recognised by coin + side + entry price + open time, and closes are inferred only when certain (complete list, shown closed, or a newest-first page that covers the position). Followed portfolios are pseudo-wallets `invo:<portfolio id>` (sources 'invo_scout' + 'invo_bridge', display_name '<username> · note'), so the tracker, follow signals, follow exits and Mimic treat them like wallets; every open counts (no size floor). Unreadable visits are kept in `invo_bridge_raw`; `invo_bridge_runs` is the health log, and the tracker warns in agent_logs ('INVO BRIDGE') when rounds stop or Invo looks logged out. Why: follow paper and unmatched Invo traders directly from Invo, without APEX calling Invo's API or holding Invo credentials.
- Weekly Invo re-scout: the bridge opens `SCOUT_PAGES` (Invo leaderboard) about once a day and APEX keeps the raw responses in `invo_bridge_raw` ('scout:leaderboard'). The scheduled "APEX Invo re-scout" agent reads them plus Mimic results and changes the scouted list only through service_role-only `invo_follow_set(address, username, note)` / `invo_follow_drop(address)` (max 30, paper only). Why: the follow list refreshes itself, and traders are kept or dropped on APEX's own after-fee copy results rather than Invo's stats.
- Mimic simulator (`src/lib/sm/mimic.ts` pure + tests, `mimic.server.ts` I/O): up to 20 active, profitable Invo traders (`sm_scores.mirror`) get $100 virtual copies in `mimic_trades`, opened when `trackWatchlist` sees them open and closed when they close, after Invo fees. No review, no risk rules, never touches the paper desk or live. Why: measure whether copying Invo traders the way the video does pays after fees and delay.
- Research connectors (CoinMarketCap, LunarCrush) are used only by the scheduled signal-review agent, never by app code. Coinversa Pulse is a fallback candidate source, used only if the Hyperliquid copy gate fails (`docs/fallback/coinversa-candidates.sql`, not applied). Why: wallet scores come only from Hyperliquid's own data.
- Content Rewards (Whop clipping): `cr_*` tables with owner-only SELECT and no client writes. External agents write only through service_role-only SQL functions (`cr_upsert_campaign`, `cr_add_clip`, `cr_set_clip_stage`, `cr_record_post`, `cr_update_post_metrics`, `cr_log_agent_run`); `cr_set_clip_stage` refuses 'approved' and posting needs an approved clip. The owner approves and edits through owner-checked server functions. Why: same pattern as `submit_review()`, and no clip goes live without the owner's approval.
- Navigation: every signed-in page renders inside `AppShell` (sidebar + Ctrl/Cmd+K palette) from `_authenticated/route.tsx`; menu groups live only in `src/components/nav/nav-config.ts`, so pages don't add their own nav links. Restore sidebar preference after hydration; mobile navigation closes its drawer after selection. Content Rewards is a separate company (contentrewards.com) that uses Whop only for payouts; its 10% creator fee comes off CPM payouts (`WHOP_FEE_PCT` in `src/lib/cr/logic.ts`). Why: one menu to maintain, and estimates match the terms.
- Per-setup trade management lives only in `MGMT` / `mgmtFor` in `engine.ts` (targets, partial size, break-even, time stop, stop-distance band), used by the backtest, the paper desk and paper sizing. `volume_breakout` (4H close beyond the prior 18-bar range on >2x the 48-bar average volume, on the side of the coin's 4H EMA200; stop 3x 4H ATR; half off at +1R with the stop left in place, the rest at +4R or after 42 bars) is paper only until someone adds it to `live_setups`. Paper-only columns `paper_budget_usd`, `paper_risk_pct`, `paper_max_open`, `paper_max_same_side` override the shared ones for paper; the live desk keeps `budget_sek`, `risk_pct`, `max_open`. Why: one definition of how each trade is managed, and new setups prove themselves on paper without changing the real-money rules.
- Strategy research runs offline in `research/strategy-lab/` (Python, data exported from `hl_candles`/`hl_funding`). A setup is adopted only after the engine re-implementation matches the lab on the same data and passes both halves of an uncapped backtest. Why: fast experiments without research code in the app, and backtest numbers that don't depend on which coins happened to get the slots.
- Owner's sizing rule `SIZE_UP` (`src/lib/hl/risk.ts`, also used by `sizeLive`): when the reviewer's confidence (review.confidence, chance of reaching T1 before the stop) is 70 or more and the normal size is too small to split into two halves above the $10 minimum, the trade is sized up just enough to split, never above $40, and the max-risk check is skipped for that step. The night rule is off (owner wants entries 24/7). Why: the owner accepts a larger position only on high-confidence trades so T1/T2 can split on small accounts.
